## 2. The Deep Dive directive (before any build)

The Deep Dive is a SEED project run with the owner and the operations seat. Its order is
fixed:

1. **The systems access map first.** Every system the plan touches, who grants access to it
   (from the session's "[Name] can grant [system]" lines), what the machine will connect to,
   and the card status. Written to `ACCESS-MAP.md`. The first cards go out the same day, one
   at a time, to the named grantor, for what Phase 1 needs. Where no grantor was named, the
   machine asks; it never guesses.
2. **The real context, Phase 1 first.** SOPs and process documents into `context/phase-N/`,
   eyes on the actual screens with the operations seat walking the job, access only through
   the map's cards, and a real number or a week-one measurement plan for every baseline still
   marked "no number known".
3. **The brainstorm, per opportunity.** Every part, deeply, in their words, until the build's
   shape is genuinely understood: what goes in, what the machine does, what comes out, the
   home of each piece, what stays human, the sandbox rule, the session's constraints, the
   verification on real work, the cards it will need.
4. **The record.** `design/phase-N.md` the moment the design is approved.
5. **Graduation.** The owner agrees the context is complete. Phase 1 graduates first and is
   sized to show a working result inside seven days of starting the build.

## 4. Standing duties, every session

- Read `BUSINESS.md`, these directives, the active phase's design record, and the plan state
  before doing anything else.
- Keep the scoreboard current. Run the week-one baseline measurements before Phase 1 builds.
- Keep `amendments.md`: route every new idea to its phase and say where it landed.
- Surface confirm-list items in status only. Never nag.
- **Design records:** write the record the moment a design is approved; read the active
  record before every working session; before executing an approved design, ask any remaining
  clarification questions first. Build only when clear.
- **The systems ledger:** keep `SYSTEMS.md` current for every external thing built or
  touched. Locations, never credentials. It is the maintain-mode checklist and the
  finish-line inventory.
- **Human-witnessed verification:** every verification item ends with a named person seeing
  the real result. The machine's own success signal is never proof.
- **Capability honesty:** never claim an always-on piece exists until it runs on its rail and
  has fired on a real event that a person saw.
- **The hand-off card:** one at a time, five steps at most, prepared in full before it is
  handed over, keys never through chat, verified with the owner watching, recorded.
- **Backup before change, commit after every session.** The repo is the backup.
